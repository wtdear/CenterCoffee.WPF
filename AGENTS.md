# CenterCoffee.WPF — правила проекта

## Назначение проекта

Это локальное WPF-приложение для кофейни «Центр кофе». Система должна постепенно
покрыть склад, поступления и закупки, продажи и заказы, меню для посетителей,
сотрудников и отчёты. Сейчас проект находится на стадии прототипа: реализованы
оболочка приложения и базовый склад, остальные модули развиваются отдельными
вертикальными срезами.

Перед реализацией спорного поведения смотри `docs/PROJECT_AUDIT.md`. Этот файл
фиксирует известные ограничения текущего ТЗ и вопросы, решения по которым ещё
нельзя молча угадывать в коде.

Актуальные согласованные решения находятся в `docs/PROJECT_DECISIONS.md`.
Если новая задача противоречит этому документу или затрагивает отмеченный там
открытый вопрос, сначала остановись и запроси уточнение.

## Приоритеты работы

1. Не ломать работающий сценарий склада при добавлении нового модуля.
2. Сначала уточнять бизнес-правило, затем менять доменную модель и только потом
   интерфейс.
3. Делать небольшие законченные вертикальные срезы: домен → use case → хранение
   → ViewModel → XAML → проверка сценария.
4. Любое изменение, влияющее на существующие данные, должно иметь план обратной
   совместимости, миграции или явного отказа от старой схемы.
5. Не добавлять настоящие данные заказчика, секреты и персональные данные в git.

## Технологические ограничения

- WPF на .NET Framework 4.7.2.
- Старый формат `.csproj`, язык C# 7.3; сборка выполняется MSBuild из Visual
  Studio, а не предположительным `dotnet build`.
- Не использовать nullable reference types, file-scoped namespaces, target-typed
  `new`, records и другие возможности новее C# 7.3 без отдельного решения о
  смене целевой платформы.
- Не подключать NuGet-пакеты и не менять target framework только ради одной
  небольшой функции. Сначала проверить, можно ли решить задачу средствами
  текущей платформы.
- Форматирование и именование должны соответствовать существующему коду:
  4 пробела, `PascalCase` для публичных членов, `_camelCase` для приватных
  полей, русские пользовательские сообщения.

## Архитектура и границы слоёв

Зависимости направлены внутрь:

```text
WPF → Application → Domain
WPF → Infrastructure (только composition root/регистрация)
Infrastructure → Application/Domain (реализация контрактов)
```

### Domain

- Содержит сущности, value-like типы, enum, инварианты и интерфейсы репозиториев.
- Не знает о WPF, JSON, файлах, MessageBox, ViewModel и конкретной БД.
- Состояние сущностей меняется через осмысленные методы, а не через публичные
  сеттеры.
- Валидация обязательных значений находится в домене. Ошибки бизнес-правил —
  `DomainException`; ошибки аргументов — в стиле существующего `Guard`.
- Денежные суммы и количества — `decimal`; не использовать `double` для денег,
  цен, остатков и скидок.
- Идентификаторы сущностей — `Guid`, даты операций — сохраняемые значения, а не
  дата, вычисляемая в UI.
- Не удалять исторически значимые записи физически без явного требования.
  Предпочитать `IsActive`, отмену или статус, если данные участвуют в истории.

### Application

- Содержит сценарии использования и координацию нескольких репозиториев.
- Транзакционные изменения (например, продажа с расходом ингредиентов и записью
  движения) должны проходить через один use case и один `IUnitOfWork`.
- UI не должен напрямую изменять доменные сущности или репозитории.
- Сервисы не должны возвращать WPF-типы и показывать диалоги.

### Infrastructure

- Реализует контракты хранения и работу с файлами/БД.
- Текущее JSON-хранилище — временная реализация локального persistence, а не
  причина протекания JSON-деталей в Domain/Application.
- Сохранение должно быть атомарным и не должно молча затирать повреждённую базу.
- При изменении формата данных повышать `schemaVersion` и добавлять явную
  миграцию/совместимое чтение.
- Не выполнять миграции или замену хранилища в рамках несвязанной UI-задачи.

### WPF

- Соблюдать MVVM: View содержит разметку, стили и минимальное подключение
  оконных событий; бизнес-логика находится в Application/Domain.
- ViewModel отвечает за состояние экрана, команды, фильтрацию отображения и
  преобразование ошибок в понятные сообщения.
- Диалоги подключаются через сервис вроде `IDialogService`; не вызывать
  `MessageBox` из Domain/Application.
- Для новых экранов сначала описать состояния загрузки, пустого списка,
  ошибки, сохранения и отмены.
- Не копировать бизнес-расчёты в конвертеры и XAML.
- Сохранять единый стиль `Resources/Theme.xaml`; не вводить локальные цвета,
  размеры и тексты без необходимости.

## Правила данных и бизнес-операций

- Остаток не редактируется напрямую: только приход, списание, продажа,
  возврат, инвентаризация или другой явно названный тип операции.
- Каждое движение должно быть связано с позицией, количеством, остатком после,
  моментом, инициатором и источником операции настолько, насколько это нужно
  для аудита.
- Нельзя считать отмену заказа завершённой, пока не определено, какие движения
  по складу и деньгам она создаёт.
- Названия «заказ», «продажа», «поступление», «закупка», «списание», «возврат»
  должны иметь отдельные определения. Не использовать их как синонимы.
- Рецепт товара должен ссылаться на ингредиенты и валидироваться до проведения
  продажи; изменение рецепта не должно задним числом менять уже проведённую
  продажу.
- Расчёт итогов, скидок, себестоимости и остатков выполняется в одном месте,
  покрывается проверкой и не дублируется в нескольких ViewModel.
- Пустая база после установки — допустимое и ожидаемое состояние. Демоданные
  можно добавлять только через явно обозначенный тестовый/демо-механизм, не в
  production-startup.

## Зафиксированные продуктовые ограничения

- Целевой сценарий первой версии: один планшет и одна локальная установка.
- Авторизация, сотрудники и права доступа не входят в первую версию. При этом
  нельзя проектировать текущие операции так, чтобы последующее добавление
  инициатора или роли было невозможно.
- Продажа считается завершённой только после оплаты и выдачи заказа. Точный
  момент списания ингредиентов должен быть одинаковым для всех сценариев и быть
  явно определён в use case; его нельзя выбирать случайно в UI.
- В первую версию входят поставщики, закупочные документы, накладные и частичные
  поставки, даже если экран закупок будет развиваться поэтапно.
- Валюта расчётов — российский рубль. Валюта не заменяет единицы измерения
  остатков: единицы хранения, закупки и рецептур нужно определить отдельно.
- НДС, скидки, бонусы, сертификаты и налоговые отчёты не входят в первую версию.
- Меню для посетителей остаётся отложенным модулем; не добавлять его бизнес-
  логику в склад или продажи без отдельного требования.
- Резервное копирование и перенос данных должны поддерживать отдельный файл.
  Формат, команда/кнопка, версия файла и проверка восстановления должны быть
  частью отдельного сценария, а не ручным копированием рабочего файла вслепую.

## Работа с задачами и изменениями

Перед кодированием:

1. Найти существующие сущности, интерфейсы, сервисы и XAML аналогичного модуля.
2. Зафиксировать затронутый сценарий и критерии приёмки.
3. Проверить незакоммиченные изменения (`git status`, `git diff`) и не затирать
   работу пользователя.
4. Если требование неоднозначно и затрагивает деньги, остатки, права или
   историю — задать вопрос, а не выбирать скрытое поведение.

После кодирования:

1. Сборка решения через MSBuild.
2. Ручная проверка главного изменённого пользовательского сценария.
3. Проверка пустого состояния, неверного ввода, повторного сохранения и ошибки
   хранилища для затронутого экрана.
4. Проверка, что не изменились `bin/`, `obj/`, `.vs/`, локальная база и секреты.
5. В итоговом сообщении указать изменённые файлы, проверку и оставшиеся риски.

## Запрещённые shortcuts

- Не реализовывать бизнес-логику в code-behind, XAML-конвертерах или обработчиках
  кнопок.
- Не обходить доменные инварианты прямой записью приватных полей, публичными
  сеттерами или ручной правкой JSON.
- Не использовать `catch (Exception) { }`, не скрывать ошибки сохранения и не
  подменять ошибку пустым списком.
- Не добавлять seed-данные при старте приложения.
- Не переписывать текущий JSON на SQLite/SQL Server в рамках задачи, если это не
  отдельная согласованная задача по миграции persistence.
- Не менять или удалять пользовательские незакоммиченные изменения.

## Локальные инструкции агентов

Специализированные профили находятся в `.opencode/agents/`:

- `requirements-analyst` — проверяет ТЗ, термины, сценарии и критерии приёмки;
- `domain-reviewer` — проверяет инварианты, транзакции и модель предметной области;
- `persistence-reviewer` — проверяет JSON/БД, миграции, целостность и восстановление;
- `wpf-reviewer` — проверяет MVVM, UX-состояния и доступность интерфейса.

Они не заменяют основного исполнителя: итоговое решение и изменения должны
соответствовать этому файлу и актуальному согласованному ТЗ.
